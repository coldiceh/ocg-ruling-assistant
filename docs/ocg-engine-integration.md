# OCG 引擎连接

本仓库保留独立 OCG sidecar 的 HTTP 客户端和本地启动脚本。引擎核心、卡片脚本和资源快照由 [ocg-sim-core](https://github.com/coldiceh/ocg-sim-core) 维护。

当前公开问答通过资料检索和最终模型生成回答，不调用模拟器、形式引擎或 Legacy Lua 旁路。配置 `OCG_ENGINE_URL` 或 `RAG_AUTO_ENGINE_SIMULATION` 不会改变这一公开路径。以下说明用于连接和检查独立 sidecar，不代表正式裁定能力验收。

## 本地启动

先按引擎仓库的说明安装依赖和资源，确保其中存在 `tools/serve.mjs`。本项目默认寻找相邻的 `游戏王游戏引擎` 目录，也可显式指定：

```powershell
$env:OCG_ENGINE_ROOT = "D:\Projects\ocg-sim-core"
pnpm dev:with-engine
```

启动脚本会检查引擎健康状态和 Legacy Lua 能力，启动或复用匹配的本地引擎，再启动后端和前端。已有监听进程不兼容、令牌不匹配或能力检查失败时，会报告错误。

默认端口：

| 服务 | 地址 | 可配置变量 |
| --- | --- | --- |
| 引擎 | `http://127.0.0.1:8790` | `OCG_ENGINE_PORT`、`OCG_ENGINE_URL` |
| 后端 | `http://127.0.0.1:8787` | `BACKEND_PORT` |
| 前端 | `http://127.0.0.1:4173` | `FRONTEND_PORT` |

引擎 profile 默认为 `ygopro`，可通过 `OCG_ENGINE_PROFILE` 设置。新启动的本地引擎使用自动生成的令牌；连接已有引擎时需提供对应的 `OCG_ENGINE_TOKEN`。

## 健康检查

本项目提供 `GET /api/engine`，转发 sidecar 的 `/health` 状态；引擎未配置或不可达时返回 503。Vercel 接口只接受 `GET` 和预检 `OPTIONS`，不公开模拟操作。

```powershell
Invoke-RestMethod -Uri "http://127.0.0.1:8787/api/engine"
```

若服务端显式设置 `RAG_FORMAL_ENGINE_MODE=formal-shadow` 或 `shadow`，该健康接口还会查询形式引擎能力。这是能力探测，不会让公开答题请求开始执行形式裁定。

## 远程连接

在独立主机部署 sidecar，通过 HTTPS 入口访问它，并在后端环境中设置：

```text
OCG_ENGINE_URL=https://engine.example.com
OCG_ENGINE_TOKEN=<与sidecar一致的令牌>
OCG_ENGINE_TIMEOUT_MS=20000
```

令牌只保存在服务端环境变量中。Vercel 环境变量修改后需要重新部署，再通过 `https://<后端域名>/api/engine` 检查连接。

原生引擎运行在独立主机，本项目的 Vercel 函数仅作为 HTTP 客户端。引擎主机的资源安装、更新和对局运行方法以引擎仓库文档为准。

## 客户端边界

- `backend/ocgEngineClient.mjs` 保留显式提交场景到 `/simulate` 的客户端，并核对返回的资源标识和摘要；模拟结果固定为非官方来源。
- `backend/formalEngineClient.mjs` 保留能力协商和形式分析客户端；接口记录与证书的检查不等于对实际裁定正确性的验收。
- Legacy Lua 客户端用于独立的脚本资料读取，其结果不能充当官方裁定。
- 上述客户端的存在不表示它们接入了公开问答流程。公开路径隔离由测试覆盖。

## 引擎复现段的显示（2026-10-16）

实验性的引擎复现段（`ENGINE_REPRO_ENABLED` 打开时运行，代码在 `backend/engineRepro/`）跟在主回答后面。段落里点名所用引擎是 ygopro（MyCard 版核心）。主回答正文里只放给用户看的短段，逐步回放不再拼进正文：

```
【ygopro 引擎复现（实验性）】已复现
结论：在 ygopro 里，我方在主要阶段1可以发动「超融合」。
依据的引擎观察值：
- 我方在主要阶段1可以选择「发动超融合」
局面：我方手卡 超融合，额外卡组 埃翁；对方场上 对极英雄 混沌侠、毁灭凤凰人（表侧攻击）。
假设：双方无其他适用效果；我方有填充卡可供舍弃。
判断模型认为官方 Q&A【「超融合」の効果は…】与本题条件一致，以该官方 Q&A 为准；ygopro 的结果只作参考。
ygopro 只显示它运行的结果，卡片脚本可能有 bug，不代表官方裁定。
```

（2026-10-30 起的版式；“结论”一句由模型按题目写，下面的清单是它用到的引擎观察值原文，见下文“简明段生成方式”。2026-11-08 起结论按子问题逐句写：只有一个子问题时版式同上；有几个子问题时“结论：”下面每个子问题一行，见“简明段生成方式”。）

- 短段由 `backend/engineRepro/concise.mjs` 生成：`engineReproDigest(record)` 从复现记录的结构化字段（`summary.status` / `reasonCodes`、`plan.assumptions`、各分支的 `assumption`、引擎结果的 `probes` / `decisions` / `state` / `log`、分支的起始 `scenario`、`cards`、准入失败时的 `error.code`、规划失败记录）取出要显示的内容，`engineReproConciseText(digest, { officialQaMatches })` 排成文字。这部分只做机械转述，不读题面文字，不判断主回答与引擎是否一致，也不判断谁对。2026-10-30 起唯一读题面的是结论句的模型调用（`conclusion.mjs`），见下文“简明段生成方式”。
- 状态只有四类：已复现、部分复现、未复现、不适用，标题行都是“【ygopro 引擎复现（实验性）】”加状态。不适用只给状态和一句原因（原因码翻成人话）。未复现（2026-10-19 起）按引擎的失败记录（`failure.step` / `step_spec` / `decision` 和 `decisions` 里的自动放弃）写出卡在哪一步、引擎当时的情况；2026-10-30 起措辞改成玩家说法、不再先写一句笼统的原因码，例如“原因：按计划操作到第 11 步（对方发动「强制脱出装置」）时卡住了：之后对方有过发动或连锁的机会，但里面都没有这张卡，接着就到了我方的主要阶段1。”“原因：按计划操作到第 3 步（我方通常召唤「…」）时卡住了：引擎这时要我方先为「苦纹样的土像」选择表示形式（可选：表侧攻击、表侧守备），计划里没有写这一步。”部分复现里未复现的分支列在“没能复现的部分”。其他未复现原因的写法见“简明段生成方式”。引擎拒绝了某一步的应答（`engine_rejected_response`，失败记录不带步骤）时，从分支自己的 setup 取那一步，写“引擎不接受这个选择”。setup 走完但有探测点没到达（`probe_not_reached`）时，写各探测点的句子；没到达的写“要看的这段过程里我方一次也没有被询问是否发动效果，所以看不出「X」能否发动”（发动或连锁的机会、主要阶段 / 战斗阶段的行动同理）。同一分支另有探测点得出了结果（出现 / 未出现 / 核心自动发动）时，这个分支算“已观察到”，整题记“部分复现”而不是“未复现”（`aggregate.mjs` 的 `branchOutcome().observed`，2026-10-19 起）。没有失败记录时只有原因码的说法。`action_mismatch` 的原因码说法是“计划里有一步在引擎里做不到，没能走到题目要看的时点”。等待超时显示“未完成”，说明“ygopro 引擎复现在等待上限内未完成……”。
- 没有设探测的分支（题目问处理结果，2026-10-19 起）不再写“这一问没有设置检查点”，改写引擎停下时的场面：2026-10-30 起是双方场上每张卡（怪兽和魔陷，最多 12 张）各一条完整状态（见“简明段生成方式”）、变化了的基本分、离场的卡（只是处理完毕送去墓地的不算）。引擎没有返回任何区域时写“引擎没有返回场上的卡”，这条不触发结论调用。
- 处理结果题（2026-10-20 起）：计划的分支可以写 `result_cards`（最多 3 张，`{card, controller}`，卡号同样核对），短段只报告这些卡在引擎停下时的状态。停下的时刻取自引擎最后一条 `by: "end"` 的决策，2026-10-30 起写成玩家说法“到我方战斗阶段时”。2026-10-20 版只写在哪、表示形式、攻守、效果是否被无效；2026-10-30 起改为完整状态，引擎没返回的字段写“未取得”（见“简明段生成方式”和“引擎状态接口规格”）。没有结论句时，分支的 `observe`（计划写的看点，30 字内）放在该分支第一条观察值前面，例如“取消攻击后红莲魔龙是否仍被无效——到我方战斗阶段时，对方场上的「红莲魔龙」：表侧守备表示，攻击力 3000，守备力 2000，效果被无效；……未取得”。子问题标签带该子问题在题面的原话（`quoted_span`，20 字内）。起因：虹之衣 / 独角兽皇枪一题短段只列了攻守，用户看不出在回答什么；2026-10-30 属性题只打印了“攻击力 1900，效果没有被无效”，于是改成报告完整状态、由结论句按题目回答。
- 复现自己的每日预算桶（`ENGINE_REPRO_DAILY_LIMIT_USD`）或每分钟限频（`ENGINE_REPRO_MAX_PER_MINUTE`）拒绝时（`error.code` 为 `engine_repro_daily_budget_exceeded` / `engine_repro_rate_limited`），短段只有一行：“【ygopro 引擎复现（实验性）】今日额度已用完，本题没有完成 ygopro 复现。”或“【ygopro 引擎复现（实验性）】每分钟次数已达上限，本题没有运行 ygopro 复现。”原因码仍记为 `budget_exceeded`。
- 每个探测点一句话：出现、未出现、未到达、核心自动发动；只能确认到卡时注明。“是否发动 / 是否”询问（`effect_yn` / `yesno`）的探测：核心通用的“是否发动”询问（描述号 0 / 221）写“可以选择「发动X」”；其他询问不一定是发动（代替破坏、卡在处理时问对方的是 / 否），引用引擎给出的原问题，写“被询问「…」”；未出现写“没有出现与「X」有关的询问”。时点取自引擎窗口的阶段和回合玩家；战斗步骤和伤害步骤里引擎决策的阶段不变（停在“战斗阶段开始”），引擎报告了战斗时点（窗口的 `timing.at`，ocg-sim-core 2026-10-18 起）时改用它（“伤害计算前”“对方回合的伤害步骤开始时”等）。列出所有含目标的窗口的时点（没有含目标的窗口时列出全部窗口），按首次出现的顺序；同一时点的窗口连锁状态不同时在时点后注明，例如“伤害计算前（连锁 1 处理前、连锁处理完毕后）”。连锁状态取自引擎给每个窗口的字段（ocg-sim-core 2026-10-18 起：`chain_links`、`in_activation` / `in_resolution`、`after_chain_end`），用词与引擎中文回放的逐窗口行相同：连锁上还有 n 个连锁块时为“连锁 n 处理前”；在连锁 n 的发动 / 处理过程中为“连锁 n 发动中 / 处理中”；连锁为空、且同一回合、阶段、战斗时点里刚有连锁处理完毕（之后没有行动选择）时为“连锁处理完毕后”；同一时点里其余的空连锁窗口写“没有连锁时”。旧引擎没有这些字段，此时不写连锁状态。每个探测点是一条观察值；多个子问题、同题两种假设的对照分支各带标签。
- 局面：场上的卡（怪兽区、魔法陷阱区、场地区、灵摆区）全部列出（2026-10-20 起，攻击的怪兽、被攻击的怪兽也是局面的一部分；装备卡写“装备给X”）；其他区域只列题目点名的卡（主回答识别出的卡）及其区域和表示形式；填充卡和其他辅助卡只写“（另有填充卡）”或“（另有其他辅助卡）”。不写区域编号、基本分、卡组张数、先攻（基本分只在引擎停下时变化了才作为观察值写出）。假设最多列 3 条，多出的写“等”。
- 官方 Q&A 那一行（2026-10-18 起）只在“对应判断”说某条官方 Q&A 与本题正好对应时显示，否则整行不显示。原来按证据包计数分三态的写法（其中“本题没有找到官方 Q&A”在线上总是出现，因为 Gemini 证据包不填那两个计数）已删除。
  - 候选：最终模型实际拿到的证据（`selectedPromptEvidenceRefs`）里的官方 Q&A（`recordType`/`type` 为 `qa` 或 `official_qa`），只取题面字段（标题、问题、详细场景），官方答案不发；卡号占位符按离线实验的写法渲染成“日文名／中文名”。材料在准备阶段由 `buildOfficialQaJudgeInput`（`backend/officialQaCorrespondence.mjs`）生成，存在 `continuation.officialQaJudgeInput`，不进最终提示词，也不进回答对象。
  - 调用：`backend/engineRepro/officialQaJudge.mjs`，GPT-6 Luna、推理 low、输出上限 6000，请求 30 秒超时（加上预算预约 / 结算的存储调用，最坏约 39 秒），走引擎复现自己的官方 API 调用和每日预算桶（不占每分钟次数）。单次请求形态在证据准备好后、最终模型调用前启动；两步请求在 finalize 开始时启动，都与最终模型调用并行。
  - 等待：引擎段先就绪；只有已复现 / 部分复现（能显示这一行）时才等判断结果，而且最多等到原来的等待截止时间（`waitDeadlineAt`，同 `ENGINE_REPRO_WAIT_BUDGET_MS`），到点不显示（`officialQaJudge.error = judge_wait_deadline`）。未复现、不适用、额度/限频、未完成和没有复现段时不等，只记录已经拿到的结果。请求体与离线实验（ocg-sim-core `experiments/official-qa-correspondence`，run-v1.1，low：判为找到 20/20 正确、应找到 21 处找到 20 处）逐字节相同。
  - 只认完成状态、且每个候选恰好一个 EXACT / PARTIAL / NOT 的输出；只有 EXACT 显示（用户口径：部分对应算没找到）。行文：“判断模型认为官方 Q&A【标题】与本题条件一致，以该官方 Q&A 为准；ygopro 的结果只作参考。”最多列两个标题，更多写“等 N 条”。没有候选、开关关闭（`ENGINE_REPRO_OFFICIAL_QA_JUDGE=off`）、预算拒绝、超时、HTTP 错误、输出不合格都不显示。
  - 只加在已复现 / 部分复现的短段里；未复现、不适用、额度/限频、未完成的短段不加。
  - 实验每题只有 2–3 条候选；线上候选可能更多，精确率不能直接外推。
- 各行之间用空行分隔，网页和按 Markdown 显示的 Bot 都会分行；观察值清单是一行引导语加若干“- ”列表项（网页渲染成列表）。
- 完整逐步回放（引擎服务渲染的全文，含每个窗口“本可发动”、区域编号、基本分、版本号、跳过的窗口数等调试信息，标题为“【ygopro 引擎复现（实验性，未经评测）】”）保留在响应的 `engineRepro.rendered` 和历史记录的 `engineRepro.rendered` 里。网页端在短段下面放一个默认折叠的“展开 ygopro 完整回放”区域，用等宽预格式化显示，保留原有换行；管理员历史记录另有“ygopro 引擎复现完整回放”一栏。API/Bot 渠道的 `shortAnswer` 只含短段。
- “仅引擎复现”按钮（2026-10-22 起）：网页在“仅准备证据包”旁边多一个按钮，发的是 `action: "prepare"` 加 `engineOnly: true`（只允许在 prepare 请求上为 true；网页渠道的字段白名单同样接受它）。证据准备完以后，同一个请求按历史记录 id 等这次准备时启动的引擎复现结果（与生成答案时的等待相同，最长到本次函数调用的等待截止），先发一个 `phase_start`（`phase: "engine_repro"`，网页显示“正在等待 ygopro 引擎复现”），再在 `prepared` 事件里带 `engineRepro: {status, questionStatus, concise, rendered}`；没有启动复现（开关关闭、题目没有识别出卡）时为 `{status: "not_started"}`。不调用最终裁定模型，也不调用官方 Q&A 对应判断；费用是证据准备和复现规划。网页显示短段和折叠的完整回放，下面仍有“生成答案”（对同一份准备只调用最终模型）。
- 响应的 `engineRepro` 另带 `concise`（短段原文）、`officialQaJudge`（判断结果摘要：状态、候选数、各判定的条数、EXACT 的条目、逐条判定与理由、耗时、费用；不含请求文本；没有判断时为 null）、`conclusion`（结论句调用的摘要，2026-10-30 起，见“简明段生成方式”）和 `digest`（短段用到的结构化数据，含编号的观察值和没复现的原因）。原来的 `officialQaState` / `officialQaDirect` 已删除。
- 计划提示词写明四种宣言步骤（`announce_card` 宣言卡名用卡号、`announce_number`、`announce_attrib` / `announce_race` 用位值），宣言的卡号与计划里其他卡号一样要在允许列表内；需要宣言不再是“搭不出局面”的理由。抹杀之指名者的决策顺序在固定版本的引擎上实测过。
- 计划提示词写明战斗时点 `at`（攻击宣言时、伤害步骤开始时、伤害计算前、伤害计算时、伤害计算后、伤害步骤结束时），步骤和探测都可写；同一张卡在几个时点都能发动时（欧尼斯特）用它指定时点。需要 ocg-sim-core 带战斗时点的引擎版本（冻结测试 P08、P09），引擎重新部署之前不要合入这一条。
- 计划提示词（2026-10-19 起）另写两条：题目问的动作（能不能发动 / 攻击 / 选择、还能做几次）只用探测，不写成 setup 步骤；连锁的回应发生在每次发动之后、开始处理之前，处理时的询问排在所有连锁窗口之后。修复轮除了失败的决策和合法选项，还会拿到失败分支的引擎中文回放（去掉标题、版本行和免责声明，过长时保留开头 1500 字和结尾 2500 字），能看出哪个窗口被自动放弃、每一步匹配到了哪里。起因：两题计划把要回应的发动写在处理时的询问之后，以及把题目问的“第 4 次攻击”写成了步骤。同日又补四句：问一个效果能不能发动时探测用 `chain`（它也算核心的“是否发动”询问；效果没被诱发时核心不询问，`effect_yn` 探测只会“未到达”，赐炎之咎姬一题本地实测）；卡文没有指定表示形式的特殊召唤（例如陷阱怪兽）在 select_place 之后还有 select_position；只有一个任意诱发、且当时没有连锁时引擎用 effect_yn 询问，写成 chain 步骤对不上、询问被自动放弃（本地实测苦纹样的土像 ③）；题目问处理结果时 setup 写到那次处理结束为止，短段列出回放结束时的场面。阿德拉 ② + 苦纹样的土像 ③ 一题在固定版本的引擎上本地实测：把“对方连锁发动”写成步骤正好得到 `action_mismatch`（引擎不给对方发动机会）；写成探测则复现成功，结果是对方没有出现发动机会（不召唤阿德拉的对照组对方可以连锁）。这与答案引用的阿德拉 FAQ 2 相反，属于引擎脚本的结果（`c91438674.lua` 的连锁限制按 `IsAllTypes(TYPE_TRAP+TYPE_CONTINUOUS)` 判断发动的卡，实测怪兽区域的土像也受限制）。

### 公开显示（阶段 4，2026-10-16 起）

2026-10-16 起引擎复现段对公开请求显示，仍为实验性功能。是否运行只看 `ENGINE_REPRO_ENABLED`：打开时，单次请求（`POST /api/answer`）和准备+生成两步请求（`action: "prepare"` / `"finalize"`）都对所有访客运行并显示，不再检查管理员会话；关闭时两种形态都不运行、不显示。

保留不变的限制：

- 复现自己的每日预算桶 `ENGINE_REPRO_DAILY_LIMIT_USD`（默认 1 美元，按 UTC 日期计）和每分钟限频 `ENGINE_REPRO_MAX_PER_MINUTE`（默认 6 次，每次复现计一次），都存在 Upstash 的独立键里，不动主回答的额度。用尽时短段只有一行（见上）。
- 等待上限：响应最多等到本次函数调用开始后 `DEFAULT_WAIT_BUDGET_MS`（`vercel.json` 里 `api/answer.js` 的 `maxDuration` 减 20 秒），可用 `ENGINE_REPRO_WAIT_BUDGET_MS` 调小；超时显示“未完成”，结果仍写入历史记录。
- 没启动的复现不等待（主流程在取到卡文之前就结束的请求，例如范围检查拒绝）。
- 历史记录（`engineRepro` 字段）和响应里的诊断字段与管理员阶段相同。

## 简明段生成方式（2026-10-30 起）

起因：用户反馈简明段“不说人话”：一道问属性的题，短段只打印了“攻击力 1900，效果没有被无效”；未复现时只说“没能生成引擎可以执行的计划”，不给原因。改法是通用的：报告什么由题目决定（一次模型调用），代码里不按题型或字段写特判；引擎能给的状态全部列出，没给的写“未取得”。

结构固定为（`concise.mjs` 的 `engineReproConciseText`）：

1. 标题行“【ygopro 引擎复现（实验性）】已复现 / 部分复现 / 未复现 / 不适用”。
2. 结论：模型按子问题逐句写（下面的结论调用；2026-11-08 起）。只有一个子问题时是“结论：<一句>”；有几个子问题时是一行“结论：”加每个子问题一项“- 子问题 n「题面原话」：<一句>”，按计划的子问题顺序。给玩家看的文字里不出现观察值编号；依据清单的每条带同样的子问题标签，可以按标签对照。
3. 依据的引擎观察值：各句用到的观察值（合并去重，按编号顺序），原样列成清单（“- ……”）。
4. 局面：计划搭的初始局面（同前）。
5. 假设：计划写的假设（同前，最多 3 条）。
6. 没能复现的部分（部分复现时）。
7. 官方 Q&A 行（同前，只在判断模型给 EXACT 时）。
8. 免责一句：“ygopro 只显示它运行的结果，卡片脚本可能有 bug，不代表官方裁定。”

没有结论句时（开关关闭、调用失败、输出不合格、预算拒绝、旧记录），第 2、3 项换成“ygopro（MyCard 版核心）的运行结果：”加全部观察值清单（最多 8 条，多的写“另有 n 条没有列出”；每个分支第一条前面带计划写的看点 `observe`）。未复现只有标题和“原因”；不适用只有标题和一句原因；额度 / 限频仍是一行。

### 观察值

`engineReproDigest(record).observations`，按记录顺序编号 o1、o2……，每条一句：

- 有探测的分支：每个探测点一条（措辞同前，例如“我方在主要阶段1（连锁 1 处理前）可以选择「发动X」”）。
- 有选卡探测（`select_probes`，2026-11-08 起，见下文“选卡探测”）的分支：每个选卡探测一条，排在探测点之后，例如“我方在主要阶段1（连锁 1 处理中）选择卡（提示「请选择要特殊召唤的卡」）时，可选：额外卡组的「方程式同调士」（效果·调整·同调 2星 光/机械 200/1500）、……；不可选：额外卡组的「测试同调调整乙」（效果·调整·同调 6星 光/机械 2400/1200）（括号里是卡片的原本数据）”。
- 没有探测的分支：`result_cards` 每张卡一条完整状态；没写 `result_cards` 时双方场上每张卡一条（最多 12 张），再加变化了的基本分、离场的卡。只有选卡探测的分支只在写了 `result_cards` 时才报告这些卡，不再列双方场上的全部卡。
- 完整状态（`normalizeCardState` / `cardStateText`）：在哪（哪一方、场上 / 场地区 / 灵摆区 / 手卡 / 墓地 / 除外 / 卡组 / 额外卡组 / 超量素材）、表示形式、种类、属性、种族、等级 / 阶级 / 连接数（连接标记）、攻击力和守备力（当前值，括号里原本值）、灵摆刻度、效果是否被无效、指示物、超量素材、装备关系（怪兽写装备卡，装备卡写装备给谁）、持续对象、持有者（与控制者不同时才写）。引擎没返回的字段在句末写“……未取得”；返回为空的写“没有……”；返回 `null` 的表示不适用，不写。哪些字段适用：引擎给了当前种类（`type`）就按种类，否则按区域（怪兽区按怪兽，魔陷区按魔陷）。离开场上的卡从引擎的移动记录写出怎么去的（“破坏、战斗，从场上送去墓地”）。
- 时刻用玩家说法：“到我方战斗阶段时”“到对方回合的伤害计算后时”，取自引擎停下的决策（`by: "end"`）的回合玩家、阶段、战斗时点（引擎给了连锁字段时加连锁状态）；没有这条决策时写“操作做完后”。
- 引擎什么都没返回（没有探测也没有局面，或没有返回任何区域）的分支记一条“空”观察值：照样列出，但不触发结论调用。

### 结论调用

代码在 `backend/engineRepro/conclusion.mjs`，由 `reproduce.mjs` 在算出题级状态之后、写入记录之前调用。

- 只在已复现 / 部分复现、且有非空观察值时调用；未复现、不适用、额度 / 限频、未完成都不调用。
- 模型：GPT-6 Luna，推理 low，输出上限 2000，请求超时 20 秒，json_object 输出。走复现自己的模型调用（生产是 `modelCalls.mjs` 的 `createOfficialModelCall`：官方 OpenAI API，密钥同规划器），调用前在复现自己的每日预算桶（`ENGINE_REPRO_DAILY_LIMIT_USD`）按最坏情况预约，结束后按实际用量结算；不占每分钟次数。
- 输入：题目原文；每个子问题在题面的原话、计划的看点 `observe`、`result_cards`、选卡探测放的对照候选（哪几张属于满足条件的一侧、哪几张属于不满足的一侧，是计划的说明）、分支假设；“小问”一节按顺序列出每个子问题和它的编号（`[q1]`、`[q2]`……，按位置编号，不用计划自己的 id）；带编号的观察值；背景（没能复现的部分及原因、假设、局面，都标明“不是观察值”）。不给主回答。
- 要求（`CONCLUSION_INSTRUCTIONS`，2026-11-08 起逐小问）：每个子问题单独一句，只回答这个子问题问的那件事；观察值里有能直接回答的事实（例如效果处理后某只怪兽出现在场上）就必须用它作答，`verdict` 为 `observed`，句子写成“引擎里的结果是……”；确实没有时 `verdict` 为 `not_observable`，句子写成“引擎记录里看不出：缺少……的观察”，写明缺的是哪一种观察（例如没有记录选卡时可选的卡），不写“引擎没有给出结果”这类笼统的话；只用观察值里的值，卡名和数值照抄；不按规则推断、不评价任何回答或官方裁定；用玩家说法，不写日志词汇。起因：棱镜一题观察值里已有“方程式同调士在我方场上”（回答了“还能拉人吗”），结论句却写成“引擎没有给出还能否拉人、是否检测素材星级的结果”。
- 输出：`{"perQuestion":[{"id":"q1","verdict":"observed"|"not_observable","sentence":"……","used":["o1"]}]}`。只检查形状：完成状态、JSON 对象、`perQuestion` 对每个子问题恰好一项（编号必须是输入里的、不能重复、不能缺）、`verdict` 取值合法、句子非空、`used` 是数组且都是输入里的观察值编号，`observed` 至少引用一条。失败原因记为 `output_not_json`、`per_question_missing`、`unknown_question:qN`、`duplicate_question:qN`、`question_missing:qN`、`verdict_invalid:qN`、`sentence_missing:qN`、`used_missing:qN`、`unknown_observation:oN`、`response_incomplete` 等。2026-10-30 的单句形状（`{"conclusion","used"}`）不再接受，记为 `per_question_missing`。不检查句子内容，没有关键词、正则、相似度之类的语义门禁。不合格、超时、HTTP 错误、预算拒绝都回退到机械清单，不改变复现状态。
- 记录：`record.conclusion.perQuestion`（每项带子问题位置 `index`、`verdict`、句子和它用到的观察值原文）、`used`（各句用到的观察值合并去重，连同文字）和 `text`（各句连起来，供日志和批量报告）。“依据的引擎观察值”就是 `used` 的原文：调用时连同文字一起存进记录，以后改了渲染代码，旧记录仍照原样显示；2026-10-30 的旧记录（只有 `text` 和 `used`）照旧显示成“结论：<一句>”。响应的 `engineRepro.conclusion` 摘要字段不变；逐句结果在 `engineRepro.digest.conclusion.perQuestion`。批量脚本 `--mock` 读的 `<qid>/conclusion.json` 也要用新形状。
- 开关：`ENGINE_REPRO_CONCLUSION` 为 0 / false / no / off 时不调用（默认开）。批量脚本同样调用，`--skip-conclusion` 关闭，`--mock` 时读 `<qid>/conclusion.json`。
- 耗时与费用记在引擎段，不计入主回答：`engineRepro.timings.conclusionMs`、`engineRepro.modelUsage` 里 `stage: "conclusion"` 一条（token、费用）、响应的 `engineRepro.conclusion`（状态、原因 / 错误、模型、推理强度、用到的编号、耗时、费用、token；不含提示词）；历史记录的 `engineRepro.timings` 带 `conclusionMs`。
- 预计（未实测，按 `estimateTokens` 和官方单价估算）：输入约 900–2100 token（1 条到 12 条观察值），输出含推理按 400–1200 token 算，每次约 0.0003–0.0008 美元；预约上限约 0.0011–0.0013 美元。耗时参考同模型同推理强度的官方 Q&A 判断（中位 4.7 秒，P95 6.9 秒，输入更长），预计 3–7 秒；它在复现跑完之后串行执行，引擎段就绪时间相应推后，超时上限 20 秒。2026-11-08 的逐小问说明比原来长约 370 token（估算 568 → 938），输入另多“小问”一节；输出按子问题数变长。这些都没有实测。

### 没复现的原因

`engineReproDigest(record).notReproduced`，未复现时列在“原因”下，部分复现时列在“没能复现的部分”下：

- 子问题搭不出：规划器写的 `unrepresentable` 原样显示，“搭不出题目说的局面——题目没说是哪张卡让你抽牌，复现器不会自己补卡”。计划提示词要求这一项写成给玩家看的一句话（60 字内）。
- 回放卡住：“按计划操作到第 n 步（……）时卡住了：……”（引擎失败记录，措辞见上）。
- 计划没通过检查：“计划没通过检查：……”后接检查器的原话；引擎拒收计划：“引擎没有接受这个计划：……”后接引擎的原话。
- 规划器没给出计划：每一轮的结果（`record.planFailures`），例如“规划模型没有给出能交给引擎的计划：第一次输出太长被截断；修复时输出的不是完整的计划”。修复输出无法解析时题级状态记为 `invalid_input`（原来原因码为空）。
- 卡名身份：“没法确认题目里的卡：「X」没能确定是哪张卡”或“「X」在 ygopro 的卡库里找不到”（`preStatus.unresolved` / `unmapped`）。
- 整次运行出错：按错误码 / 错误名写“引擎服务正忙”“引擎服务出错或暂时连不上”“规划模型调用失败”“等待引擎或规划模型超时”等（`error.code` / `error.name`）。
- 只有旧记录缺少这些细节时才退回原因码的说法；“没能生成引擎可以执行的计划”不再出现。

用词：简明段不出现“回放、日志、行动选择、窗口、决策、探测、分支”这些词（`tests/engine-repro-concise.test.mjs` 检查）；完整逐步回放仍在折叠区“展开 ygopro 完整回放”里。

## 选卡探测（select_probes，2026-11-08）

起因：棱镜一题问“检测的到素材星级吗”，引擎记录里看不出来，因为效果处理时没有记录可选的怪兽范围，额外卡组里也没放等级不同的候选；局面还把题目里对方的幽鬼兔放到我方场上当连接素材。

计划提示词（`plannerPrompt.mjs`）加两条通用规则，不点名任何卡：

- 对照候选：题目问“能不能选到 X / 检测不检测某条件 / 选择范围是否受限”时，在要选的区域（卡组、墓地、额外卡组等）同时放入条件两侧的候选，至少一张满足、一张不满足（例如等级在上限以内和超出上限的调整各一张）；setup 照常写完那次选卡（选一张会出现在可选列表里的），并在这一分支写 `select_probes`。候选由规划器自选（填充卡、相关卡、通用工具卡或 extra_cards），在 `assumptions` 里逐张写明哪张卡、放在哪里、为什么代表哪一侧。原来“题目问的动作用探测、不写成步骤”的规则对选卡范围类题目例外。
- 无关角色：题目点名的卡只充当题目给它的角色；题目没指定的素材、解放或舍弃用的卡、被选的对象、凑数的怪兽，用填充卡、通用工具卡或与题目无关的卡，不拿题目里的卡顶替；选了什么、充当什么写进 `assumptions`。`assumptions` 原来“填充卡、卡组内容不用写”的豁免收窄为“卡组里垫底的填充卡不用写”。

计划字段：`branches[].select_probes: [{after, player, candidates: [{card, from, controller?, side}]}]`，最多 3 个，每个 1–8 张候选。`after` 与引擎探测同样计数：回答这次选卡的是 setup 第 `after+1` 步，它必须是 select_card / select_unselect / select_sum / select_tribute 且玩家相同；`side` 是 `meets`（满足条件）或 `fails`（不满足），是对候选的说明，不是预测结果。计划检查（`reproduce.mjs` 的 `checkPlan`，用 `selectProbes.mjs` 的 `checkSelectProbes`）只查形状和身份：数组长度、`after` 指向的步骤、玩家一致、候选卡号在允许列表里、`from` / `controller` / `side` 取值。两侧是否都有不检查（只有测试夹具会标出缺一侧的计划），不加门禁。修复轮的分支没重写 `select_probes` 时沿用原来的，并按修复后的 setup 重新检查（步骤序号变了就报计划问题，这个分支不再运行）。

为什么不放进 `actions.probes`：引擎的探测只认 idle / battle / chain / effect_yn / yesno，而且 actions schema 不允许多余字段（ocg-sim-core `schema/actions.schema.json`），写进去整个计划会被判无效。所以 `select_probes` 留在本仓库，发给引擎的 `actions` 不变。

读取（`backend/engineRepro/selectProbes.mjs`）：引擎的 `result.decisions` 本来就记录每个决策，选卡决策带着引擎给出的全部可选卡（`options` 的 card、name、controller、from、seq）、张数上下限、阶段、战斗时点、回合玩家、连锁状态和选卡提示（`hint`，只取 HINT_SELECTMSG）。本仓库找回答 setup 第 `after+1` 步的第一条决策记录（逐张选卡时有几条，第一条列出全部可选卡），读出：

- 可选：这次选卡引擎给出的每一张卡（已经选中的不算）。
- 对照候选逐张归类：在可选列表里 → 可选；不在列表里、且按计划局面（`scenario`）放进了声明的区域、引擎的移动 / 抽卡记录（`log` 的 move / draw，按决策的 `log_pos` 截到这次选卡之前）显示那时仍在 → 不可选；之前已经离开 → “在这次选卡前已经离开……，不在可选之列”；计划根本没放进那个区域 → “计划没有把……放进……”；没有引擎日志或区域无法跟踪（场地区、灵摆区、超量素材）→ “……不在可选之列，但当时是否在……未取得”。
- 卡片数据：所有分支的选卡探测合起来只多发一次引擎 `cards` 请求，取可选卡和候选的卡库数据（种类、等级 / 阶级 / 连接数、属性、种族、攻守），观察值里写成玩家习惯的“效果·调整 2星 光/机械 200/1500”，句末注明“括号里是卡片的原本数据”。这是卡库里的原本数据，不是对局中的当前值（引擎在选卡时不报告当前值）；请求失败时注明“卡片数据未取得”，不影响复现。这次请求计入引擎耗时 `timings.engineMs`。
- 状态：读到这次选卡 `observed`；回放没走到这一步 `not_reached`；那一步回答的不是选卡 `not_card_selection`；旧引擎记录没有可选卡 `no_options`。后三种照样列出，但算“空”观察值（不触发结论调用）。

题级状态：选卡探测读到了结果，和探测点得出结果一样算“已观察到”（`aggregate.mjs` 的 `branchOutcome().observed`），只限 setup 用完后卡在必需选择、探测点没到达、询问区间没走完这三种情况；此时整题记部分复现，“没能复现的部分”写出卡住的原因。

### 选择时点候选列表接口规格（待引擎侧实现）

现状（ocg-sim-core `47049d0`）：`result.decisions[].decision` 已经给出“时点、玩家、候选卡 code/name”——选卡决策的 `index`、`kind`、`player`、`phase`、`timing.at`、`turn_player`、`chain_links` / `in_activation` / `in_resolution` / `after_chain_end`、`hint`、`min` / `max` 和 `options`（每项 `card`、`name`、`controller`、`from`、`seq`；select_unselect 另有 `selected`，select_sum 另有 `param` 和 `must`）。缺的是“每张是否可选”：ygopro-core 的 MSG_SELECT_CARD / SELECT_UNSELECT_CARD / SELECT_SUM / SELECT_TRIBUTE 只列出能选的卡，不满足条件的卡根本不出现。本仓库目前按上一节从计划局面和移动记录推断；推断不了时写“未取得”。

建议引擎给每条选卡决策加一个字段：

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| `zone_cards` | `[{card, name, controller, location, seq, selectable, level, rank, link, attribute, race, attack, defense, type}]` | 这次选卡时，可选卡出现过的每个（控制者，区域）里的全部卡，`selectable` 为布尔；数值字段是此刻的当前值（同“引擎状态接口规格”的查询位，不适用写 `null`，查不到就省略键） |

- 时点和玩家沿用决策本身的字段，不重复。
- 区域范围按可选卡所在的（控制者，区域）取，不读卡片脚本、不猜效果检索的范围。可选列表为空时核心通常根本不询问，这次选卡就不会出现，这个字段也帮不上；这种情况计划里那一步会对不上（未复现，写出卡住的原因）。
- 客户端接入方式：有 `zone_cards` 时，候选是否可选、此刻数值都以它为准，不再从移动记录推断；没有时保持现状。验收：同一回放补上字段后，观察值里“当时是否在……未取得”消失，括号里的数据改成此刻值、句末说明随之改成“括号里是选卡时的数据”。

## 引擎状态接口规格

用途：简明段和结论句报告引擎停下那一刻卡片的完整状态。本仓库客户端（`concise.mjs` 的 `normalizeCardState`）按下列字段名解析；引擎没返回的字段显示为“未取得”。引擎侧已在 `ocg-sim-core` 的 `feat/full-card-state` / `c5e7b993772517dd623847a10d3afa7fefe64384` 实现并通过本地及 CI 的 67 项测试，尚未部署。客户端同时兼容旧响应与完整状态响应；接入不代表线上引擎已经升级。

旧响应：`POST /v1/reproduce` 返回的 `result.state.players[0|1]` 有 `lp` 和区域数组 `mzone` / `szone` / `hand` / `grave` / `removed` / `extra` / `deck`；场上的卡项有 `{card, name, seq, position, attack, defense, disabled}`（`disabled` 自 ocg-sim-core `fc0b250`），其他区域的卡项主要是 `{card, name, seq}`。`result.decisions` 最后一条 `by: "end"` 是停下的决策；`result.log` 的 `move` 事件带 `from` / `to` / `reason`。

完整状态字段：每个区域（含手卡、墓地、除外、卡组、额外卡组）的每张卡项都带；对这张卡当前种类不适用的写 `null`（例如连接怪兽的守备力、魔法卡的属性）；列表字段没有内容时写 `[]`。客户端把“键不存在”当作未取得，`null` 当作不适用，`[]` 当作没有。刻度、等级、阶级和连接数的 `null` 不转成 0；真实的 0 刻度仍显示。旧响应的非空 `counters` 十六进制键字典也会按实际种类和数量显示，不当作没有指示物。

| 字段 | 取值 | 来源（ygopro-core 查询位） |
| --- | --- | --- |
| `type` | 整数位标志，当前种类（TYPE_MONSTER 0x1、TYPE_SPELL 0x2、TYPE_TRAP 0x4、TYPE_EFFECT 0x20、TYPE_FUSION 0x40、TYPE_TUNER 0x1000、TYPE_SYNCHRO 0x2000、TYPE_EQUIP 0x40000、TYPE_XYZ 0x800000、TYPE_PENDULUM 0x1000000、TYPE_LINK 0x4000000 等） | QUERY_TYPE |
| `attribute` | 整数位标志，当前属性（地 0x1、水 0x2、炎 0x4、风 0x8、光 0x10、暗 0x20、神 0x40，同计划提示词的宣言位值） | QUERY_ATTRIBUTE |
| `race` | 整数位标志，当前种族（战士 0x1 … 幻想魔 0x2000000，同计划提示词） | QUERY_RACE |
| `level` / `rank` / `link` | 整数，当前等级 / 阶级 / 连接数 | QUERY_LEVEL / QUERY_RANK / QUERY_LINK（连接数） |
| `link_marker` | 整数位标志（左下 0x1、下 0x2、右下 0x4、左 0x8、右 0x20、左上 0x40、上 0x80、右上 0x100） | QUERY_LINK（连接标记） |
| `attack` / `defense` | 整数，当前攻守（已有） | QUERY_ATTACK / QUERY_DEFENSE |
| `base_attack` / `base_defense` | 整数，当前的“原本”攻守（被效果改过原本数值时是改后的值）；“?”写负数 | QUERY_BASE_ATTACK / QUERY_BASE_DEFENSE |
| `lscale` / `rscale` | 整数，灵摆刻度 | QUERY_LSCALE / QUERY_RSCALE |
| `disabled` | 布尔，效果是否被无效（已有） | QUERY_STATUS 的 STATUS_DISABLED |
| `counters` | `[{type, count, name}]`，`name` 取 strings.conf 的 `!counter` 名 | QUERY_COUNTERS |
| `overlay` | `[{card, name}]`（也接受卡号数组），超量素材 | QUERY_OVERLAY_CARD |
| `equip_target` | `{player, location, seq, card}` 或 `null`，这张卡装备着谁 | QUERY_EQUIP_CARD |
| `targets` | `[{player, location, seq, card}]`，持续对象 | QUERY_TARGET_CARD |
| `owner` | 0 / 1，持有者 | QUERY_OWNER |
| `position` | 已有；除外区和额外卡组的卡也带上（表侧 / 里侧） | QUERY_POSITION |

位值和查询位已由引擎实现对照固定核心 `3209cd866a55e8501a0ed358d3064d9ae0ae6b30` 的 `common.h` / `card.cpp`（`get_infos`）核对。客户端也接受已经翻成名字的取值（字符串或字符串数组）。引擎新契约将 `counters` 改为数组，旧字典另存 `counters_legacy`；连接怪兽的 `defense` 从 0 改为 `null`。这里兼容这两种响应，不能据此保证其他引擎消费者也兼容。

其他约定：场地区的卡放在 `szone` 里时 `seq` 写 5（客户端按场地区显示），也可以单独给 `fzone`；灵摆区可以单独给 `pzone`。停下的决策（`by: "end"`）如果带上与探测窗口相同的连锁字段（`chain_links` / `in_activation` / `in_resolution` / `after_chain_end`），时刻会写上连锁状态。

验收：同一个回放，补上字段后简明段里对应的“未取得”消失；`tests/engine-repro-concise.test.mjs` 的“card state: an engine reporting every field …”就是按这份规格构造的输入。

不在这份规格里：作用在卡上的持续效果清单（例如“不会被战斗破坏”）、本回合已用过的次数限制（ygopro 查询位不直接给出，要另行设计）；卡名被效果改变后的当前卡号（要先在核心里确认 QUERY_CODE / QUERY_ALIAS 的语义再定）。

## 复现完成与询问区间（2026-10-30，本地未部署）

本次针对实际失败记录修复完成判定和修复反馈，不改题目答案、引擎核心或卡片脚本。

- setup 用完但仍等待必需的选区、选卡、宣言等，不再等同复现完成。新版引擎返回 `failure.reason=required_decision_pending`；外层仍为 `not_reproduced / action_mismatch`。正常行动边界和当前确实命中的显式询问探测仍可停止。客户端也对有足够末尾决策信息的旧 `replayed` 响应作同样检查。
- `present_auto` 只用于 `chain` 探测，不能把 CHAINING 当成 yesno/effect_yn 的询问出现。
- yesno/effect_yn 探测可以写 `until:"chain_end"`。观察自 after 步之后跨后续 setup 选择，直到实际连锁结束；结果带 `interval:{end:"chain_end",completed,log_index?}`。只有确定区间结束后，未出现询问才可报告为 absent。默认的单步区间保留原有语义，不能把旧 not_reached 直接改成 absent。
- 引擎另外提供 `setup_consumed` 和正常停止时的 `completion:{kind,decision_index?,probe_indices?}`。计数表示计划项已交给引擎，不保证题意正确；引擎拒绝响应时也可能包含被拒绝的那项。
- 修复仍最多一次。失败输入携带精确探测身份/区间、当前合法选择、可容纳时的执行进度；RetryError 保留实际决策和尝试的步骤，不传裸响应。新增诊断优先替换原回放额度，系统提示估算 4630→4598。原 16000 输入目标仍是软目标；没有新增轮数，不承诺每个请求的实际费用不增，修正旧假成功后也可能开始使用已有的修复机会。
