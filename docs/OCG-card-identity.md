# OCG card identity confirmation

The extraction model owns the individual-card mention set. Each mention retains the player's original wording and formal names in `name`, `enName`, optional `jaName` / `cnName`, and optional `canonicalNames`. All these fields, including `originalText`, are matched exactly against the names stored on the catalog record: the formal-name fields plus the record's own `aliases` (synchronized names and CID-bound community Chinese names such as Baige translations). Derived series aliases and nickname references are not record names and are not used here. One distinct identity binds directly only when the player's own wording (`originalText`) is itself one of that record's names. When the identity comes from a formal name the model supplied for other wording (an abbreviation, nickname or typo), it is a proposal: the mention stays pending with `proposedCardIds` and goes to candidate confirmation. (2026-10-12: the extractor once named an unrelated catalog card for 密告, and once named 魔女工艺·混乱结合 for 密告 in a Witchcrafter question; both bound directly before this rule.) Multiple identities remain ambiguous with all of them proposed; no match remains unresolved. A sourced nickname reference can still bind its pending mention. Query scanning is not unioned into a supplied model mention set.

Only remaining pending mentions enter candidate confirmation. Existing local name-index ranking and Baige search supply actual card records, and every proposed card is added to its mention's candidates (replacing the last surface candidate when the cap is reached). Candidates carry the catalog card kind (for example `spell/field`, `trap/counter`) when the record has no printed type line. A selected record is built from its own formal name and keeps the player's wording as `input`. Ranking cannot bind identity. The existing Luna selector receives the original question and candidate handles once; a null, absent or invalid selection keeps the mention pending. The preload result is reused by the ruling pipeline, and downstream approximate matching cannot replace an explicit non-selection.

Group surfaces without a reference (2026-10-16). The typed extractor files series-shaped wording under `groupMentions`, and those surfaces never reached the catalog or confirmation. A card name written without its suffix has the same shape: in the reported question 对极英雄 (only record 11310 对极－英雄 混沌) and 超越召唤兽 (only record 22982) were answered as "missing card text", and 至天 was confirmed when filed as a card mention but resolved nothing in a later run that filed it as a group. The extractor sees the catalog only through the local name and nickname references, and neither surface had one. Now a group surface that appears in the question, received no reference and is not part of another mention gets a mechanical listing of the catalog records whose stored names contain it (a prefix match missed 月女神之至天 for 至天, which ends that name). These are the same record names as above, after `normalizeCardKey`. With one to six owners (the per-mention candidate cap, so every owner is shown), it joins confirmation after the model's own pending mentions, as a proposal with reason `model_group_mention_catalog_name`. It shares the single selection call and the existing request limits. Only a selection binds. On a null, failed or skipped selection it is withdrawn, so the extractor's group classification stands and no new pending mention is added. A surface the extractor saw a reference for keeps its classification. Broader or ownerless surfaces are unchanged. Tests: `tests/group-mention-catalog-name-candidates.test.mjs` (scripted selections, routing only). No paid model call was made, so whether the real extractor files these surfaces as groups, and whether the selector then picks them, still needs a live check.

Hard limits per question:

- Four pending mentions, in existing mention order, sharing the one selection call.
- Two actual Baige HTTP requests total, with at most one request per processed mention. This also bounds numbered-name fallback searches.
- Four local and four Baige results per mention; stable-CID deduplication leaves at most six candidates per mention and twenty-four per question. Mentions after the Baige allowance is used rely on local candidates and proposals.
- One extra Luna call, using the existing `none` default. Confirmed identities skip candidate work.

The per-question allowance also survives an invalidated preload. The invariant is one confirmation attempt with bounded search requests; the observed signals are the same original query and the preload's recorded request/call counts. The check depends only on these mechanical facts, independently of whether the old identity snapshot is still usable. A false positive skips optional confirmation and leaves identity pending. Snapshot compatibility alone cannot enforce the allowance, because discarding a snapshot does not undo its completed requests. This boundary was reproduced by a failing regression and fixed without another paid run.

The final OCG prompt and evidence selection are unchanged. The displayed answer restates a confirmed card only when the player's wording is not one of that card's formal names (a nickname, abbreviation, community name or candidate selection), so a wrong interpretation is visible; a card typed by its formal name is not restated. TCG sources, text projection and ruleset integration remain outside this branch.

Selecting from a partial name (2026-10-16). In two live runs of 怪兽被贴到了后场算不算入至天的计数, 至天 was filed as a card mention and reached confirmation with four local candidates, 月女神之至天 (23503) second among them, and the selector returned null (`model_candidate_not_found`, owner `model_candidate_confirmation`). The candidates were present; the selection rule withheld them. It allowed a selection only when the type line and card text matched the player's description and otherwise required null, so a fragment of a name with no restated card text was declined even though only one candidate's text dealt with what the question asked. The selection prompt in `buildCardIdentitySelectionPrompt` now says that players often write only part of a name or a nickname and rarely restate card text, and asks the selector to compare what the question says about the card (what it does there, which treatment is asked about, what kind of card it is) with each candidate's type line and text. It selects only when exactly one candidate's text contains the kind of treatment the question asks about and the other candidates' texts are unrelated to it, even without a full name or restated text. It still returns null when the description fits no candidate, or when two or more fit and cannot be told apart. Name similarity alone neither selects a candidate nor is a reason for null, and no guess beyond the name may rewrite a candidate's identity. The handle, JSON and JSON-null rules are unchanged, and the prompt names no card and gives no effect example. The selection cache key includes the full prompt, so earlier cached selections are not reused. Selection reasoning comes from `RAG_CARD_BAI_SELECTION_REASONING_EFFORT`, which has defaulted to `low` since 2026-10-12 (the `none` in the hard limits above predates that change); this change leaves it as is. Tests: `tests/card-identity-selection-model.test.mjs` checks the prompt rules, and replays the routing on a synthetic catalog with scripted selections (a name written without its prefix, filed under `cardNames`, offered with every catalog record containing it, bound only through the selection). No paid model call was made, so whether the real selector now picks 23503 here, and whether it picks 11310 and 22982 for 对方场上有对极英雄和毁灭凤凰人，我可以用超融合把这两只怪融合成超越召唤兽吗？, needs a live prepare run for each question.
